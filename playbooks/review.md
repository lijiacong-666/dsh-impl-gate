# 评审环手册：把「能不能开工」变成流程的一步

本手册面向**没参与写 plan 的评审者**。评审者只读 `<outDir>/SPEC.md`，不读 `compose-plan.json`、不读实现源码。目标是在任务卡发出去之前，用一页纸判定每个模块是否真的能开工——结构闭合（materialize 通过）不等于语义自洽。

## 什么时候用

- `impl_gate_compose({mode:"materialize"})` 成功之后、`impl_gate_init` 分发之前。固定顺序：materialize → 评审 →（不合格则改 plan）→ 重新 materialize → 再评审 → init。
- 改了 plan 里任何 `types` / `data` / `errors` / `http` / `modules[].exposes` / `constraints` 之后，都要重新评审。
- 一次评审只针对一次 materialize 的产物；不同 SPEC.md 的结论不互认。
- 评审不代替 `impl_gate_check`：评审判「契约是否可开工」，check 判「实现是否符合契约」。

## 谁做

- 一个**没参与写 plan** 的独立评审者（人或另一个模型/会话），不知道 plan 里的取舍理由。
- 只读 `<outDir>/SPEC.md`。**不读** `compose-plan.json`、SPEC-DRAFT.md 之外的中间产物，也不读实现源码。
- 读不到的信息就是「需澄清」：不要替 plan 补决定，不要猜。

## 判定粒度与通过线

逐模块给一个判定，不用平均分：

| 判定 | 含义 |
|---|---|
| 可开工 | 只凭 SPEC.md 就能写出实现与测试，不需要再问任何人 |
| 需澄清 | 缺一个具体值/归属/错误体；写清缺什么，改 plan 就能补 |
| 不可开工 | 契约自相矛盾，或实现必须先改契约（按现契约写必错） |

通过线（缺省）：**模块 ≥80% 为「可开工」，且没有「不可开工」**。用户可在开工前另定通过线，但不得低于「零不可开工」；低于通过线就按「回灌规则」处理。

## 五类必查

逐模块过这五类，每条都要能指到 SPEC.md 的具体小节或原句；指不到就等于没查。

### 1. 类型字段与来源

- 契约里出现的每个类型都有字段表（`object` 有 fields，`enum`/`union` 有 values，`external` 有 source），不是只有名字。
- 每个输入类型的每个字段，都能回答「谁提供、何时校验、空值怎么办」。
- 写入路径的字段覆盖：表里 `not null` 且无 default 的列，在写它的模块签名/输入类型里有同名字段。materialize 的 G8 校验只做一层启发式（snake→camel + 签名扫描），评审要确认没有被 `Omit`/`Partial` 或嵌套 input 类型绕过去。
- 输出类型的字段与验收断言里读的字段对得上。

### 2. 表 owner、rowWriters 与 FK 写入

- 每张表都写了 `owner`（谁建表）与 `rowWriters`（谁在运行时插入/更新），两者职责分开。
- `rowWriters` 里的模块，其 `exposes` 真有插入/更新该表的签名，不是只有查询。
- 每个外键列的写入方，能拿到被引用表的主键；被引用行的创建路径在某个 rowWriter 的签名里。
- 外键列 `not null` 时，写入签名必须能带这个值（与第 1 类最后一条同源）。

### 3. 错误码形状与构造通道

- 每个 `E_` 码都有响应体形状（逐条 `shape` 或全局默认），形状与 HTTP 层的实际输出一致。
- 每个 `E_` 码都有「谁抛、在哪一层构造、需要哪些参数」；构造函数的参数要够带出 `conflicts`/`detail` 这类上下文——只有 `code` 与 `message` 的错误构造器，遇到字段级冲突就不够。
- 同一状态码不对应两个语义相同的码；错误码不跨模块重复定义。

### 4. 原子操作的共同事务句柄

- 需要「整批成功或整批失败」的操作，签名里能拿到同一个事务/连接句柄，或该模块自己拥有写入权。
- 跨模块写入的原子操作，句柄要能从调用方传到被调用方（签名参数里看得到），不能靠全局单例猜。
- 幂等/重试语义写清楚（重复提交返回什么）。

### 5. HTTP 覆盖与归属

- 每个对外路由都在 `http[]` 里，且落到某个模块 `kind:"http"` 的签名；`handler` 等于签名开头的标识符。
- 每个路由只有一个归属模块；鉴权、限流、body 限制都有明确模块负责。
- 验收断言里出现的路由都已声明；非 HTTP 模块的断言不写路由。
- 请求/响应类型与 `types` 里的定义一致，错误响应也在 `errors` 里。

## 回灌规则

1. 每条「不可开工」都要落成 **plan 字段的改动**（`types[].fields`、`data[].columns`、`errors[].shape`、`http[]`、`exposes[].signature`、`constraints` 之一）。落不进任何字段的，说明需求本身没定，写进 `openQuestions[]` 不能算通过。
2. 不许只在附录或评审表里写决定：附录不进入任何模块契约，实现者看不到，会各自发明一套。
3. 改完 plan 重跑 `materialize`，再评审**全量**模块（不是只评审改过的）。
4. **最多 3 轮**。第 3 轮仍不过通过线，就**缩小范围**：把不可开工的模块从 `modules`/`http`/`data`/AC 里一起砍掉，交付可开工的子集；不得通过降低通过线、删验收断言、或把「不可开工」改判「需澄清」来过线。
5. 每轮留记录：轮次、通过线、各模块判定、回灌了哪些字段。

## 可直接复制的评审提示词

把下面整段交给评审者，只附 `<outDir>/SPEC.md` 的路径：

```text
你是独立契约评审者，没有参与写这份 SPEC。只读 <SPEC.md 路径>，不读 compose-plan.json、不读实现源码，也不写代码。
按模块逐条判定五类必查：类型字段与来源 / 表 owner+rowWriters+FK 写入 / 错误码形状与构造通道 / 原子操作共同事务句柄 / HTTP 覆盖与归属。
对每个模块给一个结论：可开工 / 需澄清 / 不可开工，并写一句证据（引 SPEC.md 的小节或原句）。缺信息就判「需澄清」，不要替作者补决定、不要猜。
输出一张表：模块 | 结论 | 必查项编号 | 证据 | 需改的 plan 字段。最后一行给：可开工 x/N 个模块、是否有不可开工。
全文不超过 600 字，禁止写代码或实现建议。发现契约自相矛盾（例如 not null 列在写入签名里没有对应字段）直接判「不可开工」。
```

## 与 materialize/init 的关系

- `impl_gate_compose` 的返回值里有 `review.playbook`（本文件绝对路径）、`review.specPath`（`<outDir>/SPEC.md`）与 `review.rubric`（`["可开工","需澄清","不可开工"]`），plan 与 materialize 两种模式都会返回。
- 评审通过之前不要 `impl_gate_init`：卡片一发出去，实现者就会按各自理解补契约。
- 评审结论不要写进生成的 SPEC.md（下次 materialize 会覆盖）；它属于对话/评审记录，回灌只落在 plan 字段。
