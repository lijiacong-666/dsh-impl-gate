# 0.4.35 — 草稿模式的向后兼容，以及一个指错文件的提示词

## 查了什么

`mode:"draft"` 是「plan 已存在时只刷新 SPEC-DRAFT.md」的路径。此前没人测过它遇到 **0.3.x 形状的旧 plan**（没有 `flows`/`ui`/`runtime`，类型没有 `owner`/`unit`，路由没有 `auth`/`status`/`query`）会怎样。

实测结论：**行为本来就是对的**——旧 plan 通过校验，草稿照常渲染；连 `deliverables` 整段删掉也只是进 `missingSlots`（`plan: deliverables`），`problems` 为空，草稿仍然写出来。设计上「草稿永不阻塞」是成立的，只是没有测试守住。

## 修了一个真问题

草稿模式返回的评审提示词仍然指向 `<outDir>/SPEC.md`——而草稿阶段只有 `SPEC-DRAFT.md`，`SPEC.md` 还不存在。评审者照着提示词会打开一个不存在的文件。

改法：`composeReview(outDir, specFile = 'SPEC.md')`，草稿分支传 `'SPEC-DRAFT.md'`；提示词随文件切换语义：

- 草稿：这是草稿，不做「可开工」判定，逐节列空着/待定/互相矛盾的地方，并回给写 plan 的人
- 收尾一句改成「草稿阶段不调用 `impl_gate_review`，等 materialize 产出 SPEC.md 之后再评审」

## 新增测试

`tests/compose-draft.test.mjs`（4 例）：

1. 0.3.x 形状的 plan（删掉七类新字段）→ `ok`、`problems` 空、草稿写出
2. 删掉 `deliverables` → 仍然 `ok`，`missingSlots` 含 `plan: deliverables`
3. 草稿不重写 `compose-plan.json`（sha256 前后一致），且 `review.specPath` 指向 `SPEC-DRAFT.md`、提示词含「草稿」「不调用 impl_gate_review」
4. `materialize` 的评审仍指向 `SPEC.md`（不会误指 DRAFT）

## 已知缺口

- 旧 plan 的兼容只到「字段缺失」；如果旧 plan 用了已改名的字段（例如 0.2.x 的某些键），`validatePlan` 仍会报 `unknown field`，draft 会把 `problems` 原样带出但不阻塞——没有自动迁移。
- 草稿的 `missingSlots` 只认 plan 级必填项，模块内部空槽仍要靠读草稿发现。
