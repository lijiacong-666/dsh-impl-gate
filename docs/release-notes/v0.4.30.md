# 0.4.30 — 警告目录自证一致

## 改了什么

新增 `tests/warnings-manifest.test.mjs`（4 条断言），把「警告目录」当成一个承诺来守：

1. `src/host/compose/materialize.ts` 的 `ComposeWarning` 联合类型里有多少个码
2. `docs/WARNINGS.md` 的表格是否逐条列出同样的码（集合相等，顺序无关）
3. 两份 README 里「共 N 类 / There are N kinds」的 N 是否等于实际数量
4. 每个码是否至少被一个测试提到（排除本测试自身）

## 为什么

这类数字最容易被外部读者当证据：README 写 37 类、表格只有 35 行、代码里 38 个码，三种情况都不会让任何测试失败。之前靠人工数，现在靠一条断言。下次加警告时忘了写文档，`pnpm test` 会直接红。

## 实测

```
$ node --test "tests/*.test.mjs"
# tests 317
# pass 312
# fail 0
# skipped 5
```

四个断言一次通过，说明当前状态确实是：代码 37 个码 / 表格 37 行 / README 37 类 / 每个码都有测试提及（`TYPE_OWNER_MISSING` 的覆盖在 `tests/type-owner.test.mjs`，不在 `warnings.test.mjs`）。

## 已知缺口

- 这条守卫只检查「码是否存在」，检查不了「表格里的触发条件与消法是否过时」——那部分仍要靠人读。
- 如果将来把警告码改成从配置/数据文件生成，这个测试要跟着改成读数据源，而不是读 `materialize.ts`。
