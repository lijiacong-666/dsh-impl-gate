# 0.4.31 — 手册字段与 schema 对齐（抓到一处真漏洞）

## 改了什么

新增 `tests/playbooks-manifest.test.mjs`（11 条断言）：把 `plan.ts` 里的八个键集合（`ROOT_KEYS`、`MODULE_KEYS`、`TYPE_KEYS`、`TYPE_FIELD_KEYS`、`ERROR_KEYS`、`HTTP_KEYS`、`HTTP_QUERY_KEYS`、`FLOW_KEYS`）逐个与 `playbooks/compose.md` 对账；另加三条：三种模式都被提到、`review.md` 保持三态判定与通过线、评审证据必须能指到 `SPEC.md:<行号>`。

## 抓到的真漏洞

`TYPE_FIELD_KEYS` 里的 **`unit`** 在 `compose.md` 里完全没提——0.4.10 加了这个字段、写了警告（`UNIT_MISSING`），但**唯一的说明书没写**。也就是说：模型按手册写 plan，永远不会写 `unit`，然后被自己的警告一直点名。

已在 `compose.md` 的 `types` 行补上：字段结构示例带 `{name:"currentQuantity",type:"number",unit:"片"}`，并说明「单位不写进字段名时尤其需要」。

## 为什么值得

手册是模型唯一的输入。schema 里有、手册里没有的字段，等于不存在；反过来，手册里教一个不存在的字段，模型会写出 `PLAN_INVALID`。这类断层不会让任何测试失败——直到有人照着写。

## 实测

```
$ node --test "tests/*.test.mjs"
# tests 328 / pass 323 / fail 0 / skipped 5
```

11 条新断言里，冒烟阶段失败的那条（`SPEC\.md:\d+`）是因为手册里写的是占位符 `SPEC.md:<行号>`，不是数字——改成接受两种写法后通过。

## 已知缺口

- 只核对「键名被提到」，核对不了「解释是否正确」。手册里把 `auth` 说成三种之外的值，这条断言抓不到。
- 八个集合是硬编码的；新增一个键集合（例如以后加 `events`）时，要把名字加进测试，否则新集合不受保护。
