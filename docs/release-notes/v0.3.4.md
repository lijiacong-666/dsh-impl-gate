# v0.3.4 — 查询参数进契约

本版把 `http[].query` 补上，解决实写实验里的 G-2：`ExerciseQuery` 三个字段声明为必填，但 AC 里传 `{}`，实现者只能猜「到底哪些参数可选」。

> 本版同时包含尚未发布过的 v0.3.3（`types[].owner`、`TYPE_OWNER_MISSING`、错误对象契约）。

## 改动

- `http[].query`：`{name, type, required?, note?}[]`。不写 `required` 视为可选。`name` 必须是普通标识符；`type` 若是自定义类型（大写开头）必须已在 `types` 声明。
- `SPEC.md` 4.4 节新增「查询参数（契约的一部分）」一段，逐条列出 `- GET /api/sessions — month（string，必填）、page（number，可选） — 从 1 开始`。
- playbook 的 `http` 行补 `query` 写法与反例（把查询参数塞进 `req` 类型里）。

## 升级注意

- 老 plan 不带 `query` 时行为不变，只是 GET 路由若仍用 `req` 表达查询参数，文档不会替你说明哪些必填。
- 建议把只用于查询参数的类型从 `req` 移出，直接写进 `query`，`req` 只留请求体。

## 已知缺口

- `data[].aggregates`（聚合/统计口径）尚未建模，报表类需求仍要靠自由文本。
- 仍未校验「owner 模块的 files 里是否真有这个类型的定义」。
- 未定义行为（排序规则、越界处理）仍靠 `constraints`/`openQuestions`，工具不能判断「这里本该有定义」。
- 评审环抓矛盾、抓不到留白：唯一可靠的发现方式仍是照着文档手写一个模块。
