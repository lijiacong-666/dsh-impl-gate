# v0.3.3 — 共享类型归属与错误对象契约

承接 v0.3.2 的实写实验：那份 SPEC 里还有两处只能靠猜的地方——六个跨模块 DTO 没有一个归属文件，以及 AC 断言 `err.code` 却没人说错误对象长什么样。这版把这两处补成契约。

## 改动

- `types[].owner`：共享类型写明由哪个模块的文件定义并导出。`SPEC.md` 4.2 的类型块下渲染「归属：M1」，任务卡 3.1 同步出现。`owner` 必须是已存在的模块 id，否则 `/types/<i>/owner: module "M9" does not exist`。
- 新警告 `TYPE_OWNER_MISSING`：一个类型被两个以上模块引用、却没有 `owner` 时提示——这是「每个模块各造一份 DTO」的源头。注释：只为本地使用的类型不必写 owner。
- `SPEC.md` §8 的「接口约定」固定增加一条错误对象契约：抛出的值必须 `instanceof Error`、带 `code: string`（取自 §4.3）与可选 `details: unknown`。
- playbook 的 `types` 行补 `owner` 说明与反例。

## 升级注意

- 老 plan 不写 `owner` 时行为不变，只是会多出 `TYPE_OWNER_MISSING` 警告（仅当该类型被两个以上模块引用）。
- `owner` 只能写模块 id，不能写路径；路径仍归 `modules[].files` 与 `deliverables` 管。

## 已知缺口

- 仍未校验「owner 模块的 files 里是否真的有这个类型的定义文件」——只能检查模块存在，无法判断文件里有没有 `export type X`。
- 未定义行为（排序、分页缺省、非法参数）仍靠人写进 `constraints`/`openQuestions`，工具不能判断「这里本该有定义」。
- `http.query` 显式参数表尚未实现（实验里的 `ExerciseQuery` 三字段「声明必填但 AC 传空」仍会出现）。
- 评审环抓矛盾、抓不到留白，这条结论在 0.3.3 不变：唯一可靠的发现方式仍是照着文档手写一个模块。
