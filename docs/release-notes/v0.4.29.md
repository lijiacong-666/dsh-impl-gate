# 0.4.29 — 发布卡片改成实际走法

## 改了什么

`playbooks/30-release.md` 描述的是模板的发布流水线（tag → CI → OIDC → GitHub Release）。实际这边走的是「本地暂存发布 + 浏览器批准」，两条路完全对不上。现在新增一节 **In this repository (2026-11): staged publish, approved in the browser**：

- 为什么不走 OIDC：npm 账号的 2FA 是安全密钥（passkey），CLI 无法完成 WebAuthn，`npm publish` 直接 403；Bypass-2FA token 已被弃用且页面不再提供勾选框
- 实际命令：`npm whoami` → `npm stage publish`（打印 `staged with id <uuid>`）→ 在 npmjs.com 的 **Staged Packages** 用 passkey 批准
- 只能网页批准的原因：`npm stage approve <id>` 需要 OTP，且它打印的授权 URL 被脱敏成 `***`
- 发布后核对：`npm view dsh-impl-gate version dist.shasum` 与 `npm pack --dry-run --json` 的 shasum 对齐
- 三条本仓库特有的注意：版本/tag/`lib/` 必须一起动；GitHub 443 期间可以只推 tag 到本地、之后补推；旧 tag 当时没触发 workflow 的，用 API 补建 Release 是允许的，但同一版本不能打第二个 tag
- 暂存版本改不了：发现问题时 bump 补丁版本重新 stage，拒绝旧 stage 也要走浏览器

同时把 Step 6 的验证命令改成真实可用的（原来的 `pnpm smoke <name>@X.Y.Z` 签名早就不存在了），并在 `playbooks/20-npm.md` 顶部加一条指向该节的提示。

## 为什么

发布是唯一「做错一次就要人肉收尾」的动作。卡片写的路径如果跑不通，下一个维护者（或下一个 AI）会照着做、失败、再猜——比没有文档更费时间。

## 实测

- `playbooks/30-release.md` 142 行，新增节位于 `## Preconditions` 之前
- `playbooks/20-npm.md` 第 4 行是新增的 Passkey 提示
- 文中命令均来自本机实际执行记录（stage id、403 原文、`***` 脱敏现象）

## 已知缺口

- GitHub Actions 的 OIDC 发布路径仍未配置；如果以后切到 Trusted Publishing，这一节应改成「可选的本地方案」
- 发布流程仍有一半依赖人工点浏览器——这是 npm 的账号策略决定的，不是脚本能绕过的
