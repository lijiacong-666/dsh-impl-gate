# v0.3.2 — 成功状态码、响应头、留白清单

这一版只做一件事：把「照着文档写代码时，仍然必须自己猜」的地方补成契约。来源是一次外部实写实验——评审者只读一份 1272 行 SPEC 手写一个模块，列出 12 处只能靠猜的空白，其中 3 处是模型缺字段，其余是生成 doc 时丢掉了 plan 里已有的信息或根本没要求写。

## 改动

- `http[].status`：成功状态码进入模型。缺省 200，`res:"void"` 缺省 204；`status:204` 但 `res` 不是 `void`、或 `res:"void"` 却写了别的状态码，都是 `PLAN_INVALID`。`SPEC.md` 4.4 新增「状态码」列。
- `http[].resHeaders`：属于契约的响应头（如 `X-Row-Count`）可以写死，4.4 节单独渲染「响应头（契约的一部分）」；空名或空值报 `/http/<i>/resHeaders`。
- GET / DELETE 的 `reqExample` 渲染成「查询参数示例」，不再标成请求体。
- playbook 新增 4 条常见坑：DTO 只写进 `types` 不归属文件、成功状态码留白、未定义行为（排序/分页/非法参数）不写、依赖版本与测试方式不落地。

## 升级注意

- 老 plan 不带 `status`/`resHeaders` 时行为不变（200 / void 204 / 无额外响应头）。
- 如果你的 plan 里已经写了 `status: 204` 但 `res` 不是 `void`，升级后会直接 `PLAN_INVALID`——这是有意的，之前那类写法让实现者无法判断到底有没有响应体。

## 已知缺口

- `types[].owner` 尚未实现：共享类型仍然没有归属文件，只能靠 `deliverables.files` 与模块白名单人工对齐（实验里 6 个 DTO 无处安放）。
- 未定义行为仍靠人写进 `constraints` 或 `openQuestions`，工具只能提示 `COVERAGE_GAP`，不能判断「这里本该有定义」。
- 依赖版本与测试命令仍写在 `stack`/`globals.conventions` 的自由文本里，不做版本解析。
- 评审环抓「自相矛盾」，抓不到「留白」：实验 12 条空白里五轮评审命中 0 条。留白的唯一可靠发现方式是照着写一遍。
