# 0.4.44 — 发布前自检脚本 + 一页审批说明

## 为什么

发布这一步踩过的坑，全是「本地都对、到浏览器前才发现不对」：

1. 版本 bump 了，但没写 `docs/release-notes/v<version>.md`
2. 版本 bump 了，但没重新构建（`lib/` 里还是旧版本号）
3. 同版本重复 stage（`E409 Cannot stage previously published version`）
4. tarball 漏了 `docs/`，或把 `tests/` 带上了

这四件事都能在 30 秒内本地查出来，不该留到人工审批时才失败。

## 新增 `scripts/release-check.mjs`

```bash
node scripts/release-check.mjs     # 或 pnpm release:check
version   0.4.44
tarball   91 files, 195k bytes (unpacked 583k)
notes     present
release preflight ok — stage it, then approve in the browser
```

四项检查：版本号 → notes 文件 → git tag 能解析 → `lib/index.js` 含当前版本 → 解析 `npm pack --dry-run --json` 的文件表（不得含 `tests/`，必须含当版 notes）。任一不过 → 打印 `problem …` 并退出 1。

实现细节：`npm` 在 Windows 上是 `npm.cmd`，`execFileSync('npm', …)` 会 `ENOENT`，所以用 `execSync` 走 shell。

## 新增 `docs/RELEASE-QUEUE.md`

给「最后点 Approve 的人」看的一页：

- **结论**：只批最新一版，其余 Reject（tarball 含全部改动，中间版本没有独立价值）
- 审批前 30 秒核对命令
- 四类事故与脚本如何拦住
- 顺序（Reject 旧 stage → Approve → 核对 shasum → 升级 profile → 确认七个工具）
- 为什么队列长：CLI 过不了 passkey，每轮 stage 都留在服务端
- GitHub 443 恢复后的两条 push 命令

`scripts/check-package.mjs` 的 required 列表加入该文件，tarball 会带出去。

## 测试

350 tests / 345 pass / 5 skip；`pnpm verify:full` 全绿（含 smoke 四份样例：mini/fitness/pillbox/run-log 的警告数与卡片数未漂移）。

## 行为变化

- 新增 `pnpm release:check` 脚本；不影响既有命令。
- **从这一版起不再自动 stage**：攒够一批再 `npm stage publish` 一次，避免队列继续膨胀。

## 已知缺口

`release-check` 不检查「stage 是否已经在 npm 上挂着」——`npm stage` 没有查询接口（只能网页看）。所以「同版本已 stage」仍靠 `E409` 事后发现，只是现在会在 stage 之前先跑本地检查，能减少一部分失败。
