# 0.4.18 — 请求体类型也要对得上

## 改了什么

- 新增警告 `HTTP_REQ_MISMATCH`（第 35 类）：POST/PUT/PATCH 路由声明了 `req: X`，而处理函数唯一参数的类型不是 `X` 时提醒：

  ```
  POST /api/medicines declares req MedicineInput, handler handleCreateMedicine takes MedicinePatch
  ```

- 只比「`T` 这种简单类型名」；处理函数有两个及以上参数（如 `(tx, input)`）时跳过——那时参数顺序本身没被契约约束，硬比会误伤。
- GET/DELETE 不参与：那是把查询参数写进 `req` 的建模错误（应该用 `http[].query`），已在 `QUERY_PARAM_UNMAPPED` / `QUERY_DEFAULT_UNSTATED` 一侧覆盖。

## 实测

| plan | `HTTP_REQ_MISMATCH` |
|---|---|
| pillbox | 0 |
| run-log | 0（首版 3 条误报全部来自 GET 路由把 `WeekQuery` 写进 `req`，方法过滤后归零） |
| fitness | 0（同源 1 条误报） |
| mini | 0 |

正样本：把药箱 `handleCreateMedicine` 的参数类型改成 `MedicinePatch`，立刻报出上面那行。

## 升级注意

- 旧 plan 若把 GET 的查询参数写在 `req`，本检查不报——但那是另一类问题，建议顺手改成 `query`。
- 处理函数签名里带默认值或解构（`({ id }: Params)`）时跳过。

## 已知缺口

- 只比类型名字面量；`Partial<X>` 与 `X` 视为不同但会被跳过（泛型不解析）。
